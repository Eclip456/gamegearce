# gamegearce

My attempt at making a Sega Game Gear emulator for the TI-84 Plus CE.

**Status:** games run with graphics and controls, but not at full speed yet.
There is no sound: the calculator has no speaker.

Controls: arrows = D-pad, `2nd` = button 1, `alpha` = button 2, `mode` =
Start, `+`/`-` = draw every Nth frame, `clear` = quit.

A game needs about 48 KB of free RAM while it runs (for a copy of the code
it's executing), on top of GGCE itself.

## Converting a game

ROMs can't be sent to the calculator as-is. Convert a `.gg` file with Python 3:

```sh
python3 tools/gg2ce.py "Sonic the Hedgehog.gg" --name SONIC --title "Sonic" -o out
```

This writes `SONIC.8xv` (the header) plus one `SONICpXX.8xv` per 16 KB ROM
page. Send **all** of them to the calculator with TI Connect CE, into Archive.

- `--name` is the on-calc prefix: 1-5 characters, uppercase letters and
  digits, starting with a letter. Each game needs a different one.
- `--title` is what shows up in the game list.

Only use ROMs of games you own, or homebrew.

## Building

Install the [CE C toolchain](https://github.com/CE-Programming/toolchain)
(CEdev), put its `bin` folder on your `PATH`, then:

```sh
make
```

The program ends up in `bin/GGCE.8xp`. Calculators on OS 5.5 or newer need a
jailbreak such as arTIfiCE to run assembly/C programs.

GGCE also needs the CE C libraries on the calculator. Send `clibs.8xg` from
the [CE libraries releases](https://github.com/CE-Programming/libraries/releases/latest)
once; without it GGCE stops with a "needs LibLoad" message.

## How it works

| File | What it does |
| --- | --- |
| `src/z80core.s` | The Z80 CPU in eZ80 assembly, generated by `tools/gen_z80core.py` |
| `src/z80.c` | Interrupts and HALT around it; also a complete C version of the CPU, used on a PC for testing |
| `src/gg.c` | The Game Gear: Sega mapper, RAM, controller and Start button ports, line timing |
| `src/vdp.c`, `src/render.c` | The video chip and the scanline renderer |
| `src/emu.c`, `src/main.c` | The game list and the screen while a game runs |

The assembly core keeps the Z80's A, F, B, C, D, E, H and L in the same eZ80
registers, so most arithmetic is a single native instruction (the eZ80's
flags match the Z80's apart from two undocumented bits). Game code runs from
a RAM copy of the ROM slots, so execution can run from one 16 KB bank into the
next even though each page is a separate AppVar.

After changing `tools/gen_z80core.py`, regenerate the core:

```sh
python3 tools/gen_z80core.py
```

## Tests

```sh
cd tools && python3 -m unittest -v        # ROM converter
make -C tests check                       # Game Gear machine and renderer (C core, on a PC)
tests/zex zexdoc.com                      # Z80 instruction exerciser (C core)
```

The assembly core runs on the calculator, so its tests run in
[CEmu](https://github.com/CE-Programming/CEmu)'s core without a TI OS (see
`bench/README.md` for building `bench/cemu/run`):

```sh
make -C tests/calc && make -C tests cputest      # every instruction, both cores
tests/cputest c.bin
bench/cemu/run -d asm.bin tests/calc/bin/GGCPU.8xp
python3 tests/cpucompare.py c.bin asm.bin       # must report 0 differences

make -C tests/calc-gg                           # the machine test, assembly core
bench/cemu/run tests/calc-gg/bin/GGMACH.8xp
```

`bench/` measures speed the same way GGCE does: the C core ran ZEXDOC at
4.6% of a real Game Gear, the assembly core at 24%.

## ROM file format

Header AppVar (`PREFIX`):

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 7 | `GGCEHDR` |
| 7 | 1 | format version (1) |
| 8 | 1 | system (0 = Game Gear) |
| 9 | 1 | page count (0 means 256) |
| 10 | 4 | ROM size in bytes, little endian |
| 14 | 4 | CRC-32 of the padded ROM |
| 18 | 32 | title, NUL-terminated |

Page AppVar (`PREFIXpXX`, XX = page number in hex): `GGPG`, page number,
format version, 2 reserved bytes, then 16384 bytes of ROM.
